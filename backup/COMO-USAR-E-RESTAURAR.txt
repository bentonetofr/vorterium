BACKUP DO VORTERIUM - COMO USAR E COMO RESTAURAR
Escrito em 14/11/2026, depois que o Supabase bloqueou o site por excesso de trafego.

===========================================================
O QUE ESTE BACKUP GUARDA
===========================================================

Cada vez que voce roda o backup.bat, ele salva na pasta
D:\baixados\programacao_reserva\vorterium-backups :

  vorterium-AAAA-MM-DD.sql        o banco inteiro (estrutura + dados),
                                  igual ao do CRM
  vorterium-dados-AAAA-MM-DD.sql  so os dados (usado para levar tudo
                                  para um projeto novo, caso B)
  vorterium-auth-AAAA-MM-DD.sql   as contas de login: e-mails e senhas
                                  (ja embaralhadas), com os mesmos ids
  storage\                        TODOS os arquivos do site: retratos,
                                  imagens das anotacoes, documentos,
                                  avatares (uma pasta por bucket)
  backup.log                      uma linha por rodada: quando foi, se
                                  deu certo e quantos arquivos vieram

NAO guarda: as configuracoes do painel do Supabase (login com
Google, URLs permitidas, modelos de e-mail) e o codigo do site
(esse fica no GitHub). Se um dia criar um projeto novo, essas
configuracoes se refazem pelo painel (veja o CASO B, passo 6).

CUIDADO COM ESTES ARQUIVOS: tem dados privados dos jogadores e as
senhas embaralhadas. A pasta fica FORA do projeto de proposito,
para nunca ir parar no GitHub. Nao mande por chat nem suba em
nuvem aberta.


===========================================================
CONFIGURAR (so uma vez)
===========================================================

Na pasta D:\baixados\programacao_reserva\vorterium-backups
(o backup.bat cria ela na primeira vez; pode criar na mao) coloque
dois arquivos de texto:

1) conexao.txt  - UMA linha, a string de conexao do banco, do
   mesmo jeito que o do CRM: no painel do Supabase, botao Connect,
   aba Direct, opcao Session pooler, porta 5432, com a senha do
   banco no lugar de [YOUR-PASSWORD].

2) chave.txt  - DUAS linhas, assim (sem aspas, sem espacos):

     SUPABASE_URL=https://SEU-PROJETO.supabase.co
     SUPABASE_KEY=cole-aqui-a-chave-service_role

   A URL e a mesma do VITE_SUPABASE_URL do .env. A chave fica em
   Project Settings > API Keys. Use a service_role (na aba Legacy
   API Keys, se o painel mostrar as chaves novas).

   ATENCAO: a service_role passa por cima de toda a seguranca do
   banco. NUNCA ponha ela no .env do site, no GitHub nem em
   nenhum lugar fora deste arquivo.


===========================================================
COMO FAZER O BACKUP
===========================================================

Abra o Docker Desktop, espere ele ficar verde e de dois cliques
no backup.bat (pasta backup do projeto). Ele confere cada passo e
mostra na tela BACKUP CONCLUIDO ou O BACKUP NAO FOI FEITO, com o
motivo. Se aparecer PARCIAL no backup.log, o banco foi salvo mas
algum arquivo do Storage falhou: rode de novo.

Quando rodar:
  - uma vez por semana, no minimo;
  - ANTES de rodar uma migration nova ou mexer no banco;
  - logo depois que o site voltar ao ar (a primeira vez baixa
    todos os arquivos, uns 130 MB hoje).

Gasto de trafego do Supabase: a primeira rodada baixa tudo; as
seguintes baixam so os arquivos novos (o nome de cada arquivo e
unico e ele nunca muda), mais uns poucos MB do banco. Como o
limite gratis e 5 GB por mes, o backup semanal e barato.

Para agendar no Windows (o PC e o Docker Desktop precisam estar
ligados na hora). Cole no PowerShell:

  schtasks /create /tn "Backup Vorterium" /tr "D:\baixados\programacao_reserva\vorterium\backup\backup.bat /auto" /sc weekly /d SUN /st 12:00

(nada foi agendado ainda; so existe se voce rodar o comando)


===========================================================
ANTES DE QUALQUER RESTAURACAO
===========================================================

FACA UM BACKUP DO ESTADO ATUAL, MESMO QUEBRADO. Rode o
backup.bat agora. O arquivo de hoje tem tudo que foi feito depois
do ultimo backup bom. Se voce restaurar por cima sem isso, perde
as duas coisas: o que sumiu E o que foi feito desde entao.

E NAO SAIA RODANDO COMANDO NA PRODUCAO COM PRESSA. Meia hora
pensando nao piora nada; um comando errado piora muito.


===========================================================
CASO A - PERDA PARCIAL (alguem apagou algo, o site segue de pe)
===========================================================

A ideia: levantar uma copia antiga do banco na sua maquina, achar
o que sumiu e devolver SO aquilo. A producao nunca e derrubada.
Voce NAO pode jogar o backup inteiro por cima da producao: isso
apagaria tudo que foi feito depois dele.

PASSO 1 - Suba um Postgres descartavel:

  docker run --rm -d --name restauro -e POSTGRES_PASSWORD=temp -p 5433:5432 postgres:17

Espere uns 10 segundos.

PASSO 2 - Crie os papeis que o Supabase tem e o Postgres puro nao:

  docker exec -i restauro psql -U postgres -c "create role anon; create role authenticated; create role service_role; create schema auth;"

PASSO 3 - Carregue o backup nessa copia:

  docker exec -i restauro psql -U postgres < D:\baixados\programacao_reserva\vorterium-backups\vorterium-AAAA-MM-DD.sql

Vao aparecer erros sobre funcoes do Supabase que nao existem
localmente. IGNORE: so interessam os dados.

PASSO 4 - Confira:

  docker exec -it restauro psql -U postgres -c "select count(*) from campaigns;"

PASSO 5 - Com a copia antiga na mao, descubra o que sumiu e
devolva so isso. Depende do que aconteceu: CHAME O FRANCISCO OU
O CLAUDE. Nao existe comando unico que sirva para todo caso.

PASSO 6 - Quando terminar:

  docker stop restauro

Arquivo isolado que sumiu do Storage: esta em
vorterium-backups\storage\NOME-DO-BUCKET\... com o mesmo caminho
que tinha no site. Suba de volta pelo painel (Storage), ou rode o
passo 5 do caso B (ele reenvia tudo e pode rodar quantas vezes
quiser).


===========================================================
CASO B - PERDA TOTAL OU MUDANCA PARA UM PROJETO NOVO
===========================================================

Vale tambem para "o projeto atual esta bloqueado e vamos mudar
para outro". NAO foi ensaiado de ponta a ponta com um projeto
real. Se der para ensaiar com calma, ensaie UMA VEZ num projeto
de teste antes de precisar de verdade.

PASSO 1 - Crie o projeto novo no Supabase, regiao Sao Paulo
(sa-east-1). Anote: a URL, a chave service_role, a chave anon e a
string de conexao (Connect > Direct > Session pooler, porta 5432).

PASSO 2 - Recrie a ESTRUTURA rodando as migrations da pasta
supabase\migrations do projeto, em ordem de nome, no projeto novo
(painel > SQL Editor, uma por uma, ou pelo Supabase CLI com
"supabase link" e "supabase db push"). Elas criam tabelas,
politicas de acesso, funcoes, gatilhos, buckets e o tempo real.
As migrations mais novas que o backup nao importam: rode todas.

PASSO 3 - Jogue os DADOS (so os dados, a estrutura ja existe):

  docker run --rm -i postgres:17 psql "STRING_DO_PROJETO_NOVO" -1 -v ON_ERROR_STOP=1 -c "SET session_replication_role = replica;" -f - < D:\baixados\programacao_reserva\vorterium-backups\vorterium-dados-AAAA-MM-DD.sql

O comando e tudo-ou-nada (opcao -1): se der qualquer erro, NADA
e gravado. Nesse caso, pare e peca ajuda em vez de tentar de novo
no escuro.

PASSO 4 - Devolva as CONTAS de login (mesmos ids, mesmas senhas):

  docker run --rm -i postgres:17 psql "STRING_DO_PROJETO_NOVO" -1 -v ON_ERROR_STOP=1 -c "SET session_replication_role = replica;" -f - < D:\baixados\programacao_reserva\vorterium-backups\vorterium-auth-AAAA-MM-DD.sql

PASSO 5 - Devolva os ARQUIVOS do Storage. Crie um arquivo
chave-novo.txt na pasta vorterium-backups (mesmo formato do
chave.txt, com a URL e a service_role do projeto NOVO) e rode:

  docker run --rm --env-file D:\baixados\programacao_reserva\vorterium-backups\chave-novo.txt -e ORIGEM=/backup/storage -v D:\baixados\programacao_reserva\vorterium-backups:/backup -v D:\baixados\programacao_reserva\vorterium\backup:/app:ro node:22-alpine node /app/storage-restaurar.mjs

Termina com uma linha RESUMO; falhas=0 e o que voce quer ver.

PASSO 6 - Refaca as configuracoes do painel no projeto novo:
  - Authentication > Providers: ligar o Google (client id e
    secret) e o login por e-mail, como estavam;
  - Authentication > URL Configuration: Site URL e as URLs
    permitidas de redirecionamento (a do site no ar e a de teste);
  - Authentication > Email: modelos de e-mail, se voce mexeu.

PASSO 7 - Troque as chaves no site: VITE_SUPABASE_URL e
VITE_SUPABASE_ANON_KEY, no .env e no lugar onde o site esta
hospedado (variaveis de ambiente). Faca um novo deploy. Todo
mundo precisa entrar de novo no site uma vez.

PASSO 8 - Confira: entre com uma conta, abra uma campanha, veja
uma imagem de retrato e rode uma rolagem de dado.
